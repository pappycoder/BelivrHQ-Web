# Registration checkout and expired subscriptions

Registration now creates the church/admin and a signed, 24-hour billing-only capability. It does not approve or return a workspace access/refresh session. The web proxy removes credentials from browser JSON, expires both normal cookie families and saves the checkout capability in a separate HttpOnly, same-site cookie. The signing realm uses the existing server bot-protection secret with a distinct purpose prefix; existing cryptographic formats/keys are unchanged.

The public `/subscription` screen uses `/billing/registration/*` for signup status, quote, checkout, verification and closing a pending checkout. Each endpoint verifies the capability, rechecks profile/tenant ownership and active/unarchived status, and derives the tenant from signed claims. Registration checkout cannot start another payment after a successful payment exists. Normal workspace routes do not accept this credential. A stale credential requires a normal sign-in to resume billing. Email confirmation still applies at sign-in.

Payment opens in a script-created tab with its opener removed. On return, verified server application is required; URL status and cross-tab hints are not proof of payment. The payment tab publishes a wake-up hint and closes only after verification. The original tab independently verifies, closes its payment window if necessary, requests focus, clears the checkout cookie and opens `/login?registered=1&subscription=active`. Cookie cleanup has a bounded timeout. A confirmed-tab sign-in link remains available when browser policy prevents closing. Browser focus/close restrictions cannot be overridden. Dashboard upgrades retain their authenticated endpoints and return to `/home` after verification.

Naturally expired, previously paid subscriptions retain their last legitimately paid plan for viewing/export within existing role, tenant and branch permissions. Their profile reports `subscriptionReadOnly`; write grants are removed from UI/service context. Request middleware and the plan guard reject business mutations with `SUBSCRIPTION_READ_ONLY`. Report export POST, billing operations and necessary authentication lifecycle actions remain available. Login no longer forces expired administrators away from the workspace into billing. A renewal notice explains the restriction.

Never-paid accounts do not gain paid read access. Current refund/dispute restrictions are not converted into read-only entitlement; revoked upgrades do not increase the previous paid plan. Existing records, payment references, pending mutations and encrypted vaults are unchanged. New offline write leases cannot outlive their paid period, and refreshed expired snapshots carry read-only permissions.

No schema migration is required. Build/verify both applications before coordinated deployment; promote API first, then web. The API also rejects Supabase's obfuscated existing-user signup result before creating a billable church. Do not attempt to test new registration against real recipient emails or charge a real provider during automated validation; browser/provider fixtures and disposable PostgreSQL cover the flow.

The existing standalone-worker/TCP Redis hosting requirement is separate and remains unprovisioned. Deployment of these changes does not claim that background jobs or production queue health are fixed. Hosted Supabase confirmation/Tawk settings also remain their existing provider configuration.

For rollback, revert web/API together to their previous revisions. Existing regular sessions remain valid; no data restore or reverse migration is needed. In-flight signup checkout cookies require the compatible API; retain it during a staged rollback or direct the affected user to normal sign-in and billing.

Validation: backend unit suites passed (123 suites / 2,347 tests), frontend unit suites passed (650 tests), and four billing/database integration suites passed (31 checks) using disposable PostgreSQL. Backend/frontend type checks, scoped lint, production builds, brand audits and generated assistant consistency checks passed. Browser validation includes new registration and payment-tab cases, dashboard upgrades, expired read access and mobile layout; final browser/deployment results are recorded below.
